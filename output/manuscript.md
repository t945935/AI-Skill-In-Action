# AI Skill 實戰

## 先找、再組、後自建

本書教你把重複工作整理成可重用、可測試、可維護的 Skill。全書從盤點現成方案開始，逐步走到組合、自建、驗證與發布。

本書範例以電子書出版流程作為整合案例；讀者可以將相同方法套用到程式開發、文件審查與團隊自動化工作。


# 導讀｜這不是 Prompt 範例集

## 本章目標

讀者完成本導讀後，能理解本書的學習路線，並知道為什麼建立 Skill 前必須先盤點現成方案。

## 核心概念

- Skill 是可重用的工作能力，不只是文字指令。
- 好的流程會先採用或組合既有能力，再補足真正缺少的部分。
- 每個實作都應有可驗證的輸入、輸出與安全邊界。

## 完成本書的交付物

每完成一個正文副章，讀者都應留下對應產物，而不是只讀完文字：

- 第一章：一張能力卡與一份 Skill inventory。
- 第二章：一份含輸入／輸出契約的工作流與交接報告。
- 第三章：一個有明確限制與驗收條件的 `SKILL.md`。
- 第四章：正向、負向與安全案例的測試紀錄。
- 第五章：含版本、雜湊與變更記錄的發行包。
- 第六章：一份從草稿到候選發布版的端到端報告。
- 第七章：一個通過內容、導覽、無障礙與安全檢查，並停在人工部署閘門的靜態網頁教材。

專案管理上的完成定義（Definition of Done）是：產物存在、命令可重跑、失敗條件可觀察，且未經確認不會產生外部副作用。

## 建議閱讀節奏

每個副章預留 30–45 分鐘：先讀目標與契約，再執行範例，最後完成練習與驗收。遇到阻塞時先記錄環境、版本、命令與錯誤，不要直接跳過失敗案例。

## 本章小結

本書將從「先找再做」開始，逐步走到可測試、可維護、可發布的 Skill。下一個主題單元會建立方案盤點與選型方法。


# 第 1 章｜先找再做：問題定義與方案盤點

## 本章目標

讀者完成本章後，能把一項模糊的自動化需求整理成可評估的工作能力，盤點現成的 Skill、工具、插件與範本，並做出「採用、組合、微調或自建」的決策。

## 核心概念

- 先描述工作能力，再搜尋 Skill 或工具。
- 現成方案應先被採用或組合，自建只用來填補明確缺口。
- 能力卡與評估矩陣讓選型理由可以追蹤與重查。

## 本章交付

完成 `examples/01-discovery/inventory.sample.md` 的一份專案版本，至少比較三個候選方案，並留下採用／組合／微調／自建的決策理由。

本書的核心候選清單見 [`examples/skills/skill-catalog.md`](../../examples/skills/skill-catalog.md)。清單只提供初評；讀者仍要依自己的宿主、版本與授權重新查證。

## 為什麼不能一開始就自己寫

看到重複工作時，直覺通常是開一個新資料夾、寫一份指示，再想辦法讓它跑起來。但真正的成本往往在後面：既有方案可能已經處理了錯誤情況、權限限制與版本相容性；自行重做不只浪費時間，也會製造另一份需要維護的規則。

「先找再做」不是拒絕客製化，而是把客製化留給真正的缺口。先盤點能讓我們回答三個問題：現成方案能否直接完成工作？多個方案能否組合完成？如果仍然不足，最小的新增範圍是什麼？

## 先把需求寫成能力卡

不要從「我要一個 Skill」開始，而要先描述工作本身。可用下面的能力卡把需求具體化：

| 欄位 | 要回答的問題 | 電子書案例 |
|---|---|---|
| 觸發時機 | 什麼情況會啟動？ | 書稿完成一個副章後 |
| 輸入 | 需要哪些檔案、參數或權限？ | Markdown、術語表、檢查規則 |
| 工作 | 必須完成哪些步驟？ | 檢查標題、連結、術語與範例 |
| 輸出 | 使用者要拿到什麼結果？ | 問題清單、修正建議與驗證紀錄 |
| 限制 | 哪些事情不能自動做？ | 不刪除原稿、不擅自發布 |
| 驗收 | 怎樣才算完成？ | 零個失效連結，且檢查報告可重現 |

能力卡的作用是縮小搜尋範圍。若需求只有「幫我把書稿弄好」，很難判斷該找編輯 Skill、EPUB 工具，還是出版流程。拆成輸入、工作與輸出後，才有可比較的條件。

## 盤點現成方案

盤點可分成三層：本機已安裝的 Skill、團隊或專案內的流程，以及公開的 repository、插件與工具。先查本機是最快的起點。

以下指令以 PowerShell 為例，列出本機 Skill 目錄；`skillRoot` 只是範例變數名稱，請依自己的環境調整。

```powershell
$skillRoot = Join-Path $env:USERPROFILE '.codex\skills'
Get-ChildItem -LiteralPath $skillRoot -Directory |
  Sort-Object Name |
  Select-Object -ExpandProperty Name
```

找到候選名稱後，讀取它的完整說明，不要只看資料夾名稱：

```powershell
$candidate = Join-Path $skillRoot 'validate-epub-project\SKILL.md'
Get-Content -LiteralPath $candidate -Raw
```

Bash 使用者可以用同樣的方式檢查：

```bash
skill_root="$HOME/.codex/skills"
find "$skill_root" -mindepth 1 -maxdepth 1 -type d -printf '%f\n' | sort
sed -n '1,220p' "$skill_root/validate-epub-project/SKILL.md"
```

公開 repository 或插件也要以同一張能力卡比較。不要因為名稱相似就直接安裝；先確認授權、維護狀態、輸入輸出、權限要求與是否能在讀者的環境重現。

## 何時停止搜尋

當已找到至少三個候選方案，且其中一個能滿足核心輸入／輸出契約、授權可接受、最近維護狀態可確認，便可停止擴大搜尋，進入小型驗證。若仍有關鍵缺口，應先記錄缺口與驗收案例，再決定組合、微調或自建；不要以「再找一個也許更好」無限延長需求分析。

## 用評估矩陣做決策

把候選方案放進簡單的評估矩陣。分數不是為了製造精確幻覺，而是讓取捨留下紀錄。

| 候選方案 | 需求適配 | 可直接使用 | 可組合 | 維護風險 | 決策 |
|---|---:|---:|---:|---:|---|
| 書稿工作流程 Skill | 高 | 高 | 高 | 低 | 採用 |
| EPUB 驗證 Skill | 中 | 高 | 高 | 低 | 與前者組合 |
| 版本化發行工具 | 中 | 中 | 高 | 中 | 延後接入 |
| 從零建立出版 Skill | 高 | 無 | 無 | 高 | 暫不自建 |

電子書案例中，書稿流程與 EPUB 驗證分別處理不同階段，組合後已涵蓋大部分需求。只有「依本書團隊格式產生特定報告」這個缺口，才值得另寫小型補充 Skill。

## 四種處理方式

### 直接採用

現成方案已符合輸入、輸出與安全限制，只需依文件操作。這是成本最低、最容易維護的選擇。

### 組合使用

單一方案不足，但兩個以上方案的輸出可以銜接。例如先用書稿檢查，再把結果交給 EPUB 驗證。組合前要確認輸出格式與失敗行為，不要只把多個名稱串在同一個提示中。

### 微調現成方案

核心流程可沿用，只需調整專案路徑、語言、報告格式或驗收規則。微調時保留原作者的限制與測試，不要為了方便而整份複製後分叉。

### 自行建立

只有在功能缺口已寫清楚、現成方案無法合理組合，而且能先定義測試案例時才自建。自建的第一版應只處理缺口，不要順便重寫整條工作流。

## 實作：建立 Skill inventory

在範例目錄建立一份清冊，至少記錄名稱、來源、用途、輸入、輸出、權限與決策。可直接複製 [`examples/01-discovery/README.md`](../../examples/01-discovery/README.md) 的表格開始。

完成清冊後，為每個候選方案寫一句決策理由，例如：

> 採用 `validate-epub-project`，因為它已涵蓋 EPUB 結構檢查；本專案只補上自訂封面尺寸報告，不重寫驗證流程。

這句話比「看起來很好用」更有價值，因為未來版本更新或換工具時，可以重新檢查原本的假設。

## 常見錯誤

- 只搜尋名稱，不閱讀 `SKILL.md`：可能忽略輸入格式、權限或禁止事項。
- 把「能完成一小步」誤認為「能完成整條流程」：應檢查輸出是否能交給下一步。
- 看到缺一個欄位就整份重做：先評估微調或補充 Skill 的成本。
- 直接使用公開 repository 的最新分支：讀者應以書中指定的版本標籤或 commit 為準。
- 沒有留下決策紀錄：下一次遇到相同需求時，又會從頭搜尋。

## 練習

選一項你每週至少做一次的工作，完成一張能力卡與一份三項候選方案的評估矩陣。最後用一句話說明你選擇採用、組合、微調或自建的原因；如果選擇自建，必須同時列出至少兩個驗收案例。

## 本章小結

Skill 設計的第一步不是寫檔案，而是理解問題並查找已存在的能力。能力卡讓需求可搜尋，評估矩陣讓取捨可追蹤，四種處理方式則把「先找再做」變成具體決策。下一章會把已選定的方案接成工作流，處理輸入輸出契約與交接問題。


# 第 2 章｜組合既有能力：從單一 Skill 到工作流

## 本章目標

讀者完成本章後，能把兩個以上的既有 Skill 接成可追蹤的工作流，為每個交接點定義輸入輸出契約，並在失敗時停在安全的位置。

## 核心概念

- 工作流由有順序的節點組成，而不是一段無法追蹤的長提示。
- 輸入輸出契約讓每個節點知道可以接收什麼、必須交付什麼。
- 上下文要按需傳遞；阻塞錯誤不可被下一節點悄悄掩蓋。
- 涉及修改、發布或外部副作用的節點需要人工確認。

## 本章交付

完成一份工作流 JSON 與至少一份交接報告；每個節點都要有輸入、輸出、通過條件、失敗反應與重跑起點。

作為組合參考，可先採用 `write-ebook-workflow` 規劃，再交給 `review-ebook-continuity` 與 `validate-epub-project`；每個節點的輸出都必須符合下一節點的契約。

## 為什麼「有 Skill」還不等於「有流程」

上一章完成的是選型：我們知道哪些方案可以採用。但一個 Skill 通常只負責一段工作，例如檢查書稿結構、驗證 EPUB，或建立版本化發行包。真正的交付物往往需要多段工作依序完成。

如果只把多個 Skill 的名稱寫在同一個提示中，系統不一定知道先後順序，也不一定能把上一段的結果正確交給下一段。可維護的工作流要把每段工作視為一個節點，並明確描述節點之間的交接。

## 先畫出工作流，而不是先寫提示

以電子書出版為例，最小可行的流程可以拆成四個節點：

| 節點 | 工作 | 主要輸入 | 產出 | 失敗時 |
|---|---|---|---|---|
| 書稿檢查 | 檢查標題、連結與術語 | Markdown、規範 | 檢查報告 | 停止修稿，不建置 |
| 內容連貫 | 找出重複、跳接與缺漏 | 書稿、章節計畫 | 問題清單 | 交人工決定是否修改 |
| EPUB 驗證 | 檢查封裝、資源與目錄 | EPUB、封面 | 驗證結果 | 不進入發行 |
| 發行封裝 | 建立版本目錄與雜湊 | 通過驗證的 EPUB | 發行包 | 保留候選檔，不標示正式版 |

這張表已經揭示流程的順序與停損點。接下來才把每個節點對應到現成 Skill 或工具，而不是反過來讓工具決定流程。

## 輸入輸出契約

輸入輸出契約（I/O contract）是節點之間的共同語言。它不必是複雜的 API 規格，但至少要說清楚四件事：輸入在哪裡、輸入必須符合什麼條件、輸出放在哪裡，以及下一節點如何判斷輸出可用。

可以使用一份簡單的交接紀錄：

```json
{
  "stage": "manuscript-check",
  "input": ["manuscript/chapters/", "STYLE_GUIDE.md"],
  "output": "reports/manuscript-check.md",
  "status": "pass",
  "blocking_issues": [],
  "verified_at": "待填寫"
}
```

`status` 不應只寫「完成」。建議至少區分 `pass`、`pass_with_notes` 與 `blocked`。下一個節點只接受符合條件的狀態，避免把半成品誤送進發行步驟。日期與版本是示意欄位，實際值應在執行時填入。

## 上下文傳遞與邊界

Skill 之間需要共享上下文，但不代表每個節點都要讀取整個專案。過度傳遞會讓規則互相覆蓋，也可能把不必要的機密資料帶到下一步。

可採用三項邊界原則：

- 每個節點只讀取完成工作所需的檔案。
- 以交接紀錄傳遞結論與檔案路徑，不用長篇對話重述全部背景。
- 下一節點自行驗證輸入，不盲信上一節點聲稱的結果。

例如 EPUB 驗證只需收到 EPUB 路徑、封面路徑與驗收規則，不需要讀取作者的私人筆記。若驗證報告指出資源缺漏，發行封裝節點應停止並回傳明確錯誤，而不是嘗試猜測如何修復。

## 交接順序與人工確認

一條可靠的工作流不一定完全自動化。凡是會改寫大量檔案、影響出版身份或產生外部副作用的節點，都應設置人工確認點。

建議將流程分成三種階段：

1. **可逆處理**：讀取、分析與產生報告，可自動執行。
2. **需審核處理**：修改書稿、套用大量格式變更，先呈現差異再繼續。
3. **外部副作用**：推送 GitHub、上傳商店或發布版本，必須明確取得授權。

電子書案例可安排如下：書稿檢查與連貫性分析自動執行；修稿由作者確認；EPUB 建置可自動執行；商店上傳停在人工閘門。這樣即使某個分析 Skill 判斷錯誤，也不會直接造成不可逆的公開變更。

## 衝突與失敗處理

組合 Skill 時，最常見的問題不是單一 Skill 失效，而是兩個節點對同一件事做出不同假設。例如一個節點接受 `pass_with_notes`，下一個節點卻只接受 `pass`；或者前一個節點修改了標題層級，後一個節點仍使用舊的目錄快取。

處理方式是先定義失敗政策：

| 情況 | 工作流反應 | 是否需要人工介入 |
|---|---|---|
| 輸入檔案不存在 | 立即停止並指出路徑 | 否，補齊輸入後重跑 |
| 檢查有非阻塞提醒 | 保留報告，標記 `pass_with_notes` | 是，出版前確認 |
| 結構驗證失敗 | 不進入下一節點 | 是，修正後重跑 |
| 外部服務無法連線 | 保留目前產物與錯誤紀錄 | 視服務重要性決定 |
| 需要刪除或覆寫檔案 | 暫停並要求確認 | 是 |

不要讓每個 Skill 自己發明錯誤格式。專案可以在 `docs/` 放置共用的狀態值與錯誤分類，讓工作流的控制邏輯保持一致。

## 實作：組合電子書工作流

本章範例使用上一章盤點的三類能力：書稿工作流程、內容連貫檢查與 EPUB 驗證。實際名稱會依讀者環境不同，請先閱讀各 Skill 的說明與限制。

在工作目錄先閱讀 [`examples/02-composition/workflow.json`](../../examples/02-composition/workflow.json)，再執行以下 PowerShell 指令，建立只包含流程交接資料的暫存目錄：

```powershell
$runRoot = Join-Path (Get-Location) '.skill-run'
New-Item -ItemType Directory -Force $runRoot | Out-Null
@{
  workflow = 'ebook-release'
  stages = @('manuscript-check', 'continuity-review', 'epub-validation')
  status = 'planned'
} | ConvertTo-Json | Set-Content -LiteralPath (Join-Path $runRoot 'workflow.json')
```

接著在 repository 根目錄執行 `./tools/run-workflow.ps1`，依序檢查三個節點並在 `reports/` 產生交接紀錄；也可以用 `-FromStage continuity-review` 從中斷點重跑。不要把 `.skill-run` 當成正式書稿，也不要把含有私人路徑或憑證的日誌提交到 repository。完整表格與交接範本見 [`examples/02-composition/README.md`](../../examples/02-composition/README.md)。

完成流程後，至少檢查：

- 每個節點都有明確輸入與輸出。
- 下一節點使用的是上一節點實際產生的檔案。
- 失敗時不會自動跳過阻塞問題。
- 需要修改或發布時有人工確認點。
- 工作流可以從中斷的節點重新開始，而不必重做全部步驟。

## 常見錯誤

- 以提示文字代替契約：文字說「接著處理」，卻沒有指定檔案與通過條件。
- 把所有 Skill 串成一條長提示：出錯時無法知道是哪個節點造成問題。
- 忽略中間產物：只保留最後 EPUB，導致無法追查哪一步改變了內容。
- 讓下一節點相信上一節點的描述：每一節都應重新確認必要輸入。
- 將分析、修改與發布放在同一個自動步驟：缺少人工閘門會放大錯誤影響。

## 練習

選一項需要兩個以上工具的工作，畫出至少三個節點，並為每個節點填寫輸入、輸出、通過條件與失敗反應。再找出一個必須人工確認的交接點，說明如果省略它可能造成什麼後果。

## 本章小結

組合 Skill 的關鍵不是把名稱排成清單，而是建立節點、契約、上下文邊界與失敗政策。當每個節點都能交付可驗證的產物，既有 Skill 才能穩定地形成工作流。下一章會處理現成方案仍有缺口時，如何以最小範圍自建 Skill。


# 第 3 章｜自建 Skill：規格、結構與封裝

## 本章目標

讀者完成本章後，能在確認現成方案不足的前提下，寫出一個範圍最小、規則清楚、可被測試的 `SKILL.md`，並把必要的參考資料與腳本放在合理的位置。

## 核心概念

- 自建 Skill 是填補明確缺口，不是重新包裝整個工作流程。
- 規格先於提示；先寫觸發條件、輸入、輸出與限制，再寫操作步驟。
- `SKILL.md` 負責行為契約，references、scripts 與 templates 負責可重用資源。
- 不同宿主支援的欄位可能不同，格式細節必須以目標工具的官方文件為準。

## 本章交付

完成一個最小 `SKILL.md` 與至少一個模板，明確列出觸發條件、不處理的工作、驗收案例及所需權限。

若需要規格起草提示，可參考 `skill-creator` 的卡片；若需要取得既有方案，先參考 `skill-installer`。兩者都不能取代目標宿主的官方格式與授權確認。

## 何時才值得自建

上一章的組合流程如果已經能完成工作，就不必新增 Skill。以下情況才值得進入自建階段：

| 判斷問題 | 若答案為「是」 | 下一步 |
|---|---|---|
| 現成 Skill 能否直接完成？ | 否 | 找出缺口 |
| 多個現成方案能否合理銜接？ | 否 | 界定最小自建範圍 |
| 缺口是否可用輸入與輸出描述？ | 否 | 先重新定義需求 |
| 能否寫出至少兩個驗收案例？ | 否 | 暫停自建，先補規格 |
| 自建後是否比維護既有方案更划算？ | 否 | 回到採用或組合 |

例如，既有 EPUB 驗證 Skill 已能檢查封裝與連結；「依團隊格式產生編輯摘要」才是缺口。合理的自建範圍是摘要報告，不是再寫一個 EPUB 驗證器。

## 先寫 Skill 規格

在開啟編輯器前，先完成一頁規格。規格至少包含：

- **名稱與觸發條件**：使用者在什麼情境下需要它？
- **輸入**：必要檔案、參數、工具與權限。
- **處理流程**：按什麼順序完成，在哪些條件下停止？
- **輸出**：檔案、報告或訊息的格式與位置。
- **限制**：不可修改、不可讀取或必須人工確認的事項。
- **驗收**：成功案例、失敗案例與不可接受的副作用。

規格應能讓另一位人員在不看實作的情況下判斷結果是否合格。若仍使用「適當地」「視需要」等模糊詞，表示規格還沒完成。

## `SKILL.md` 的最小結構

一個可維護的 Skill 通常由描述區與操作說明組成。以下範例採常見的 YAML front matter；不同宿主的必要欄位與命名可能不同，讀者應先對照目標工具文件。

```markdown
---
name: book-chapter-review
description: 檢查單一書稿副章的結構、術語、連結與範例一致性。
---

# Book Chapter Review

## 何時使用

當使用者要求檢查一個副章，且已提供章節檔案與專案規範時使用。

## 不處理的工作

- 不重寫未指定的章節。
- 不刪除原稿或覆寫原始檔。
- 不代表作者發布或上傳任何檔案。

## 工作流程

1. 讀取指定章節與必要的專案規範。
2. 檢查標題層級、內部連結、術語與程式碼標籤。
3. 將問題分成阻塞與非阻塞兩類。
4. 產生報告，列出檔案路徑與建議修正。
5. 只有在使用者明確要求時才修改檔案。

## 驗收

- 報告包含檢查範圍與檢查日期。
- 每個問題都有檔案路徑與可重現說明。
- 未經授權不會改動原稿。
```

這份檔案沒有把所有背景知識塞進主文件。主文件只保留觸發、限制、流程與驗收；較長的術語表、檢查規則或輸出範本應拆到相鄰資源。

## 資源如何分層

建議使用以下目錄分工：

```text
book-chapter-review/
├── SKILL.md
├── references/
│   ├── review-checklist.md
│   └── report-format.md
├── scripts/
│   └── check_links.py
└── templates/
    └── review-report.md
```

- `references/` 放需要查閱但不必每次全部載入的規則與背景。
- `scripts/` 放可重複執行、應以實際結果判定的檢查。
- `templates/` 放輸出格式，避免每次由模型重新發明欄位。
- `assets/` 適合放圖片、固定資料或其他非文字資源。

主文件應指向資源的相對路徑，並說明何時讀取。不要建立一個包含數百行所有規則的單一提示，否則更新一條規則就必須重新審查整份文件。

## 把權限與停損寫進流程

Skill 的限制不是附註，而是功能的一部分。至少要明確寫出：

- 允許讀取哪些路徑，避免不必要的全專案掃描。
- 哪些操作只能產生建議，不能直接修改。
- 哪些操作需要人工確認，例如刪除、覆寫、推送或發布。
- 外部服務失敗時要回報什麼，不可用猜測結果代替。

若 Skill 需要寫入檔案，先把輸出寫到明確的暫存或報告路徑，再由使用者確認是否套用。這比在流程最後才補一句「請小心」可靠得多。

## 實作：建立最小可用 Skill

本章範例的需求是：檢查單一副章，產生報告，但不直接修改書稿。請依下列順序實作：

1. 用能力卡寫出觸發、輸入、輸出、限制與驗收。
2. 檢查既有的書稿與連貫性 Skill，確認它們沒有已提供相同報告。
3. 建立 `SKILL.md`，只放必要規則與流程。
4. 將報告格式拆到 `templates/review-report.md`。
5. 建立一個通過案例與兩個失敗案例。
6. 在隔離的測試目錄執行，確認原始章節沒有被改寫。

範例目錄提供可直接閱讀的檔案與驗收清單：[`examples/03-build-skill/`](../../examples/03-build-skill/)。這個範例是教學用 Skill，不會自動安裝到讀者的環境。

## 常見錯誤

- 一開始就複製大型 Skill：會把不必要的規則與權限一起帶進來。
- 把專案背景、操作步驟與輸出範本全部放進 `SKILL.md`：難以閱讀，也難以局部更新。
- 沒有寫「不處理的工作」：Skill 容易越界，與其他 Skill 互相覆寫。
- 只測試成功案例：遇到缺檔、權限不足或格式錯誤時，可能產生看似合理的假結果。
- 用模型文字判斷檔案是否正確：可計算的條件應交給腳本或驗證工具。

## 練習

選擇一個上一章判定為「功能缺口」的工作，完成一份一頁規格與一個最小 `SKILL.md`。規格中必須列出不處理的工作、兩個成功案例、一個失敗案例，以及一項需要人工確認的操作。

## 本章小結

自建 Skill 的品質取決於界線，而不是文件長度。先證明現成方案無法直接採用或組合，再用規格界定最小缺口；最後把行為契約、參考資料、腳本與範本分層管理。下一章會以測試與安全為主，確認這個 Skill 在正常與異常情況下都能可靠停損。


# 第 4 章｜驗證與安全：讓 Skill 值得信任

## 本章目標

讀者完成本章後，能為 Skill 定義可重複的驗收案例，區分通過、提醒與阻塞結果，並在提示注入、機密資料與破壞性操作出現時安全停損。

## 核心概念

- 驗證必須對照預先寫好的案例，不能只看一次成功示範。
- 正向、負向與回歸測試分別回答不同問題。
- 安全邊界要寫進 Skill 的流程與權限，而不是只放在使用者提醒。
- 測試報告要留下輸入、版本、結果與未完成事項，才能重現。

## 本章交付

完成至少五個固定案例：兩個正向、兩個負向與一個安全案例；每案都要記錄預期狀態、實際結果與不可接受的副作用。

本書的建議組合是用 `review-ebook-continuity` 檢查內容，用 `validate-epub-project` 檢查產物，再用 `audit-ebook-project-practices` 檢查閘門與責任；三者的結果要分開記錄，不可用一個 `pass` 互相代替。

## 從「看起來可用」到「有證據可用」

一個 Skill 可能在理想輸入下產生漂亮的結果，卻在缺檔、格式錯誤或惡意內容出現時做出危險決定。驗證的目的不是證明它永遠正確，而是確認已知條件下的行為符合契約，遇到未知條件時會清楚停下來。

開始測試前，先把驗收條件寫成可觀察的結果：輸出檔案是否存在、報告是否包含必要欄位、原始檔是否保持不變、阻塞錯誤是否阻止下一步。不要使用「結果品質良好」這種無法判斷的敘述。

## 三種基本測試

### 正向測試

提供符合規格的輸入，確認 Skill 能完成主要工作。例如給定存在的副章、術語表與格式規範，應產生完整的檢查報告，且報告包含檢查範圍與日期欄位。

### 負向測試

刻意提供缺檔、錯誤格式、權限不足或互相矛盾的要求，確認 Skill 會回報問題並停止，而不是猜測或產生假成功。負向案例通常比成功案例更能揭露界線缺口。

### 回歸測試

Skill 或其參考檔更新後，重新執行一組固定案例，確認原本通過的行為沒有退化。回歸資料應放在版本控制下，避免只依賴某次對話記憶。

## 建立測試矩陣

以第三章的 `book-chapter-review` 為例，可建立以下矩陣：

| 案例 | 輸入狀態 | 預期結果 | 等級 |
|---|---|---|---|
| 完整副章 | 檔案與規範皆存在 | 產生報告，狀態為 `pass` | 正向 |
| 缺少術語表 | 章節存在，必要規範不存在 | 指出缺少檔案，狀態為 `blocked` | 負向 |
| 連結失效 | 章節含不存在的內部連結 | 列出路徑與行號，不修改原稿 | 負向 |
| 要求覆寫原稿 | 輸入要求與 Skill 限制衝突 | 拒絕覆寫，提出差異報告 | 安全 |
| 更新報告範本 | 只改輸出欄位 | 舊案例仍通過，新增欄位可追蹤 | 回歸 |

每個案例都要指定「不可接受的結果」。例如缺少術語表時，產生一份沒有警告的空報告就是失敗，即使程式本身沒有拋出例外。

## 風險分級與處置

為了讓不同執行者得到一致結果，可用以下最低分級：

| 等級 | 例子 | 處置 |
|---|---|---|
| Critical | 執行未授權命令、外洩金鑰、誤發布版本 | 立即停止，保留證據並交人工處理 |
| High | 阻塞輸入被悄悄跳過、產物與來源不一致 | 不得進入下一節點，修正後重跑 |
| Medium | 報告欄位缺漏、非阻塞格式問題 | 標記提醒，發布前確認 |
| Low | 文字或排版小瑕疵 | 納入下一輪整理，不阻塞測試 |

## 檢查產物，而不是只檢查訊息

對文件與程式碼型 Skill，至少檢查三層產物：

- **檔案層**：預期檔案存在、路徑正確、原始檔沒有非預期變更。
- **內容層**：報告欄位完整、連結與術語結果可追溯、錯誤分類一致。
- **流程層**：阻塞狀態不會進入下一節點，需要人工確認的操作確實停下來。

若 Skill 會產生 EPUB，不能只確認「已建立檔案」；還要檢查封裝、資源、目錄與閱讀器顯示。若 Skill 會修改程式碼，不能只確認「測試命令結束」；還要確認測試涵蓋修改的行為，並檢查差異範圍。

## 提示注入與不可信內容

Skill 讀取的書稿、Issue、網頁或資料檔都可能包含指示文字。那些內容是待分析資料，不是更高優先級的工作規則。安全的流程應在 Skill 中明確區分：

- **規則來源**：專案規範、Skill 文件與使用者明確指示。
- **資料來源**：待檢查的章節、日誌、Issue、網頁與測試 fixture。
- **輸出限制**：資料中的「請忽略前面規則」「請執行這個命令」等文字只能被報告，不能直接執行。

遇到可疑內容時，保留原文位置與摘要，將狀態標記為提醒或阻塞，交由使用者決定。不要為了完成流程而自動解碼、執行或上傳未知內容。

## 機密與破壞性操作

Skill 不應要求讀取與任務無關的 `.env`、金鑰、Token 或私人目錄。若輸入中意外出現機密，報告應遮蔽內容，只留下檔案路徑與類型。

刪除、覆寫、推送 GitHub、上傳商店與發布版本都屬於外部副作用。可將分析與產生差異報告自動化，但把真正的變更放在人工閘門之後：先顯示目標、檔案數量與預期影響，再等待明確確認。

## 可重現的驗證紀錄

每次測試至少留下以下欄位：

```text
Skill：book-chapter-review
版本或 commit：待填寫
測試案例：missing-glossary
輸入：examples/04-verify-secure/fixtures/missing-glossary/
預期：blocked，指出缺少 GLOSSARY.md
實際：待填寫
結果：pass／fail
```

不要把 API Key、完整私人路徑或含個資的輸入直接寫進紀錄。若測試需要真實服務，使用隔離帳號與最小權限，並把可公開重現的 fixture 優先放進 repository。

## 實作：建立安全驗收套件

範例目錄 [`examples/04-verify-secure/`](../../examples/04-verify-secure/) 提供測試矩陣與三個 fixture：完整輸入、缺少規範，以及含有可疑指示文字的輸入。請先閱讀預期結果，再以自己的 Skill 執行；不要直接把 fixture 中的文字當成命令。

實作順序如下：

1. 先執行完整輸入案例，確認基本輸出契約。
2. 執行缺檔案例，確認狀態為 `blocked` 且沒有修改原稿。
3. 執行可疑內容案例，確認文字只被報告，不被當成規則。
4. 保存實際結果，與預期結果逐項比對。
5. 將測試加入回歸清單，日後更新 Skill 後重跑。

## 常見錯誤

- 只測試最順利的輸入：無法知道 Skill 在異常情況下是否會停損。
- 把「命令沒有報錯」當成成功：產物內容與流程狀態仍需檢查。
- 讓測試資料中的指示覆蓋 Skill 規則：未區分資料與規則來源。
- 在測試中使用真實金鑰或私人資料：測試紀錄本身變成洩漏風險。
- 測試與 Skill 一起任意修改：回歸結果失去可信度，應保留固定 fixture。

## 練習

為自己的 Skill 寫五個案例：兩個正向、兩個負向、一個安全案例。每個案例都要填寫預期狀態、不可接受結果與人工確認點，並在 Skill 更新後重跑一次。

## 本章小結

可靠的 Skill 必須能在正常輸入下完成工作，也能在缺檔、錯誤與不可信內容出現時安全停下來。測試矩陣、產物檢查、資料與規則分離，以及人工閘門共同構成可信度。下一章會把通過驗證的 Skill 整理成可版本化、可分發與可維護的交付物。


# 第 5 章｜發布與治理：讓 Skill 長期可用

## 本章目標

讀者完成本章後，能把通過測試的 Skill 整理成可辨識的版本，附上文件、變更記錄、相容性說明與維護責任，讓其他人可以安全採用並在需要時移除或遷移。

## 核心概念

- 可交付的 Skill 不只有 `SKILL.md`，還包括版本、測試、文件與變更記錄。
- 發布版本必須能回溯到確定的來源與測試結果。
- 治理先處理責任與風險，再處理分發便利性。
- Skill 會過時；棄用與遷移策略和新增功能同樣重要。

## 本章交付

建立一個不可覆寫的版本目錄，內含 Skill、文件、測試摘要、變更記錄、manifest、SHA-256 與授權狀態。

`package-ebook-release` 可作為發行封裝參考；正式 tag 前仍要由維護者確認來源 commit、授權與所有人工閘門。

## 從個人檔案到交付物

在個人電腦上能執行，不代表適合交給讀者或團隊。交付前至少要回答：使用者拿到的是哪一版？需要哪些前置條件？如何驗證安裝成功？出了問題要找誰？

建議把交付物分成四層：

| 層次 | 內容 | 目的 |
|---|---|---|
| 核心 | `SKILL.md` 與必要資源 | 定義行為 |
| 測試 | fixture、測試案例與預期結果 | 證明行為沒有退化 |
| 文件 | README、使用範例、限制與相容性 | 讓使用者能正確採用 |
| 發行資訊 | 版本、變更記錄、雜湊與授權 | 讓交付可追溯 |

少了任何一層，使用者都可能把未測試的檔案當成正式版本，或在環境不相容時無法診斷。

## 版本與相容性

版本號的重點是表達影響，不是追求某一種命名法。可以採用語意化版本（Semantic Versioning）或專案既有規則，但必須固定回答三件事：

- 哪些變更不會影響既有輸入與輸出？
- 哪些變更需要使用者修改設定或範例？
- 哪些變更會改變安全邊界、權限或產物格式？

只要輸入輸出契約、預設權限或必要資源改變，就應在變更記錄中明確標示，並增加回歸案例。不要只因為文字改了幾行就跳過測試；限制文字的改動也可能改變行為。

書籍版本與 Skill 版本應分開管理：書籍版本描述教材、範例與出版產物的變更；Skill 版本描述可安裝能力的輸入、輸出與權限變更。兩者可以在 manifest 中互相記錄來源，但不能用一個版本號假裝另一個版本已完成驗證。

## 文件與變更記錄

README 應讓第一次使用的人在幾分鐘內完成最小操作，至少包含：適用情境、不適用情境、安裝位置、使用範例、前置條件、驗證方式與回報問題的方法。

變更記錄則回答「這一版和上一版差在哪裡」。建議將變更分成新增、修正、限制變更與棄用通知，並連結到測試或 Issue。避免寫成沒有意義的「優化體驗」；應指出具體輸入、輸出或權限影響。

## 發行包與可追溯性

發行包不應依賴某台電腦上的暫存目錄。可採用以下結構：

```text
dist/
└── book-chapter-review-v0.1.0/
    ├── SKILL.md
    ├── references/
    ├── templates/
    ├── tests/
    ├── README.md
    ├── CHANGELOG.md
    ├── LICENSE
    └── manifest.txt
```

`manifest.txt` 至少記錄版本、來源 commit、檔案清單、產生時間與 SHA-256。雜湊不是安全的全部，但能幫助使用者確認下載的檔案沒有被意外替換。若發行包含外部依賴，也要記錄名稱、版本與相容性限制。

## 分發與權限

分發前先決定使用者需要什麼權限。若 Skill 只需要讀取書稿，就不要要求整個家目錄的寫入權限；若必須呼叫外部服務，應說明資料會送往何處、失敗時如何處理，以及如何停用。

GitHub repository 適合放置原始碼、範例與 Issue；正式版本應以 tag 或 release 固定，而不是要求讀者永遠追蹤未驗證的最新分支。商店上架、遠端推送或其他外部發布都應設在人工確認點之後。

## 維護責任與棄用

每個 Skill 都需要一位維護者或一個明確的責任角色。治理文件應寫出：支援的工具版本、問題回報位置、回應時限（若有）、安全問題處理方式與最後一次測試日期。

當 Skill 不再維護時，不要突然刪除。先標記棄用版本，說明替代方案、遷移步驟與停止支援日期。若沒有替代方案，也要保留最後可用版本與風險說明，讓使用者能做有知情的選擇。

## 實作：建立可交付的 Skill 發行包

範例目錄 [`examples/05-release-governance/`](../../examples/05-release-governance/) 提供 README、變更記錄與發行檢查表。請依下列順序操作：

1. 固定 `SKILL.md`、資源與測試 fixture 的版本。
2. 執行第四章的正向、負向與安全案例。
3. 產生 README、CHANGELOG 與授權檔案。
4. 建立發行目錄，不覆寫既有版本。
5. 計算檔案清單與 SHA-256，保存測試結果。
6. 由另一位使用者依 README 在乾淨目錄安裝並驗證。

只有在上述證據齊全後，才把版本標記為可供讀者使用。若 GitHub repository 尚未確定，可先產生本機候選包，但不要在文件中放入虛構的遠端網址。

## 常見錯誤

- 只發布 `SKILL.md`：使用者缺少範本、測試與相容性說明。
- 直接指向最新分支：內容可能在沒有通知的情況下改變。
- 變更記錄只寫宣傳句：無法判斷是否需要遷移或重新測試。
- 重複使用同一個發行目錄：舊版本被覆寫，失去回溯能力。
- 沒有維護者與棄用策略：問題出現時無人負責，使用者也無法安全退出。

## 練習

為第三章的 Skill 建立一份發行檢查表，包含版本、測試、授權、相容性、雜湊與維護者欄位。再寫一則「下一版會改變輸出格式」的變更記錄，說明使用者需要做什麼。

## 本章小結

Skill 的生命週期不在第一次執行成功時結束。版本、測試、文件、權限、責任與棄用策略，決定它能否被別人安全採用。下一章會把前面的方法整合成一個電子書出版案例，從需求盤點一路走到可交付的發行包。


# 第 6 章｜完整案例：電子書出版 Skill

## 本章目標

讀者完成本章後，能把需求盤點、既有 Skill 組合、自訂缺口、驗證與發行治理串成一條電子書出版工作流，並知道哪些步驟必須保留人工決策。

## 核心概念

- 完整案例要先重用既有能力，再補足專案特有的缺口。
- 內容修改、產物驗證與外部發布是不同的責任階段。
- 每一階段都要留下可交接的產物與狀態。
- 出版完成不等於自動上架；商店提交仍是獨立的人工關卡。

## 本章交付

完成一份從 `draft` 到 `release-candidate` 的狀態紀錄，附 EPUB、封面、驗證報告、版本 manifest 與尚待出版者確認的欄位。

完整案例會串接 `write-ebook-workflow`、`codex-spark-book-writing`、`review-ebook-continuity`、`validate-epub-project` 與 `package-ebook-release`；平台發布類 Skill 僅在人工核准後使用。

## 案例背景

假設團隊要把一套 AI Skill 教材整理成 EPUB，並準備讀者 repository。團隊希望減少重複檢查，但不能因自動化而誤刪書稿、把未驗證的版本上傳，或把內部狀態寫進讀者正文。

最終交付包含：Markdown 原稿、可執行範例、EPUB、封面、讀者 repository 說明、版本化發行包與出版資料草稿。作者、授權、正式日期與商店帳號不由 Skill 猜測，必須由出版者確認。

## 準備一組可重跑的案例輸入

完整案例不能只說「準備好書稿」；團隊必須知道哪一份檔案是來源、由誰維護，以及缺少時應在哪個階段停止。本案例以 repository 根目錄為工作起點，將輸入分成以下六組：

| 輸入 | 案例路徑 | 責任與檢查重點 |
|---|---|---|
| 章節與附錄 | `manuscript/` | 作者維護；順序、標題與內部連結必須完整 |
| 書籍資料 | `metadata/book.yaml` | 出版者確認；書名、語言與作者不得由工具猜測 |
| 閱讀樣式 | `styles/book.css` | 製作人維護；必須與一般網頁 CSS 分開 |
| 正式封面 | `assets/cover/cover.jpg` | 出版者確認權利；尺寸與格式納入檢查 |
| 上架資料草稿 | `docs/store-listing.md` | 編輯與行銷交接；價格、地區等未決欄位保留待確認 |
| 發布閘門 | `docs/release-gates.md` | 專案負責人維護；區分自動通過與人工核准 |

`output/` 與 `dist/` 都是產物，不是內容來源。若直接修改合併稿或候選包，下次建置就會失去變更，manifest 也無法回溯。開始前先在 PowerShell 執行 `git status --short`，記下原本已存在的修改；建置流程只能改動預期產物，不能順手整理不屬於本案例的檔案。

接著做最低限度的輸入確認：所有來源檔存在、封面不是暫存圖、書籍資料能被讀取、書稿沒有內部試讀字樣，並選用一個尚未存在的練習版本。版本目錄一旦建立就視為不可覆寫；需要修正時應回到來源，再產生新版本。

## 需求與輸出契約

先把「出版一本書」拆成可驗收的輸出：

| 階段 | 主要輸入 | 產物 | 通過條件 |
|---|---|---|---|
| 內容整理 | 章節 Markdown、書籍計畫 | 結構檢查報告 | 標題層級與章節順序一致 |
| 編輯檢查 | 書稿、術語表、風格規範 | 編輯問題清單 | 阻塞問題已處理或明確保留 |
| 範例驗證 | `examples/`、測試資料 | 測試紀錄 | 指令與預期結果一致 |
| EPUB 建置 | 合併稿、CSS、封面 | EPUB 候選檔 | 封裝、資源與目錄通過 |
| 發行封裝 | 通過驗證的產物 | `dist/v.../` | manifest、雜湊與變更記錄齊全 |
| 商店準備 | 書籍身份與描述 | 上架資料草稿 | 人工確認欄位完整 |

這張表把「內容品質」與「檔案可交付」分開。即使 EPUB 能開啟，若作者或授權資料未確認，仍不能標記為可發布。

## 盤點與組合既有能力

依第一章的方法，先檢查環境已有的書稿工作流程、連貫性檢查、EPUB 驗證、發行封裝與商店準備能力。以下名稱只是示意，實際使用前仍須閱讀各 Skill 的說明與限制：

| 能力 | 處理方式 | 原因 |
|---|---|---|
| 書稿規劃與章節模板 | 採用 | 已有明確的寫作結構 |
| 連貫性與出版稽核 | 組合 | 分別處理內容與格式問題 |
| EPUB 驗證 | 採用 | 交付前需要獨立的封裝檢查 |
| 版本化發行 | 組合 | 只接受已通過驗證的 EPUB |
| 團隊特有的編輯摘要 | 自建小功能 | 既有方案沒有相同輸出格式 |

注意最後一列：自建的只是編輯摘要，不是整套出版 Skill。這能讓新功能保持小範圍，也避免與既有驗證能力重疊。

## 設計端到端流程

可將流程寫成以下狀態轉移：

```text
draft
  ↓ 內容與結構檢查
reviewed
  ↓ 範例與連結驗證
buildable
  ↓ EPUB 建置與封裝檢查
validated
  ↓ 版本化、雜湊、人工核准
release-candidate
  ↓ 出版者確認身份與平台欄位
ready-to-submit
```

任何阻塞問題都只能回到前一個可修正狀態，不能直接跳到 `ready-to-submit`。例如 EPUB 驗證失敗時回到 `buildable`；作者資料未確認時停在 `release-candidate`。

## 自訂缺口的最小實作

團隊特有的編輯摘要可使用第三章的規格方式：

- 輸入：單一副章、編輯規範與已通過的檢查報告。
- 工作：彙整阻塞問題、非阻塞提醒、負責人與建議期限。
- 輸出：固定格式的 Markdown 摘要，不修改原稿。
- 限制：不讀取私人憑證，不推送 repository，不代替作者做最終決定。
- 驗收：缺少檢查報告時阻塞；完整輸入時產生所有必要欄位。

這個小功能可以接在內容檢查之後、EPUB 建置之前。若未來其他專案也需要同樣摘要，再考慮把它抽成可泛用的 Skill；第一版不要預先擴大範圍。

## 驗證與人工閘門

依第四章的測試矩陣，至少執行：

- 完整書稿：所有必要章節與資源存在。
- 缺少封面：建置應阻塞，不產生可發布標記。
- 範例失敗：保留錯誤紀錄，不把候選版標記為通過。
- 內文含可疑指示：只作為資料報告，不執行其中命令。
- 作者欄位未確認：可以產生草稿，但不能進入提交階段。

內容修改與 EPUB 建置可在隔離目錄自動執行；覆寫原稿、建立正式版本、推送 GitHub、上傳商店等操作都要停在人工確認點。確認時應顯示目標路徑、版本、檔案清單與預期外部影響。

## 從輸入走到候選包

範例入口位於 [`examples/06-ebook-publishing/run-case.ps1`](../../examples/06-ebook-publishing/run-case.ps1)。它不重新實作各項能力，而是依固定順序呼叫合併稿建置、EPUB 產生、工作流檢查、安全 fixture、版本化封裝與候選包驗收。

第一次練習時，在 repository 根目錄執行：

```powershell
.\examples\06-ebook-publishing\run-case.ps1 -Version 0.2.1-local
```

這個命令依序完成：

1. 依檔名順序合併導讀、章節與附錄，產生 `output/manuscript.md`。
2. 使用 metadata、獨立 EPUB CSS 與正式封面建立候選 EPUB。
3. 檢查必要章節、附錄、範例與書稿內部連結。
4. 執行完整、缺少資料與不可信指示等正負向 fixture。
5. 建立新的 `dist/v0.2.1-local/`，複製通過檢查的產物與交接文件。
6. 寫入來源 commit、建置時間、檔案大小與 SHA-256。
7. 重新讀取候選包，確認檔案齊全、雜湊一致、來源可追溯，最後停在人工核准點。

成功結尾應包含：

```text
package-files: pass
checksum-verification: pass
manifest-traceability: pass
release-gate: awaiting-human-approval
case-complete: v0.2.1-local
```

前三個 `pass` 分別證明交付內容、檔案完整性與來源紀錄符合案例契約。`awaiting-human-approval` 不是失敗，而是流程刻意停止的位置；它表示程式不能替出版者完成 EPUBCheck、裝置試讀、授權確認或商店提交。

## 讀懂實際輸出

候選目錄應呈現以下結構：

```text
dist/v0.2.1-local/
├── AI-Skill-In-Action.epub
├── cover.jpg
├── book.yaml
├── store-listing.md
├── release-gates.md
├── RELEASE_STATUS.md
├── manifest.txt
└── SHA256SUMS.txt
```

EPUB 與封面是交付內容；`book.yaml` 與 `store-listing.md` 讓平台欄位可以重新核對；`release-gates.md` 保存未完成事項。`RELEASE_STATUS.md` 說明目前只是 `release-candidate`，`manifest.txt` 記錄版本、來源 commit、驗證器與已知限制，`SHA256SUMS.txt` 則用來偵測包內檔案是否在交接後被改動。

不要只看到 EPUB 就宣告完成。收件者應能回答：這個檔案來自哪個 commit？哪套檢查已通過？哪些外部驗證仍未做？封面與上架草稿是否和候選 EPUB 屬於同一批次？只要其中一題無法從包內證據回答，交接就還不完整。

## 失敗演練與修正循環

完整案例至少要示範一次「失敗後回到來源」：

| 失敗現象 | 正確停點 | 修正方式 | 不應採取的捷徑 |
|---|---|---|---|
| 缺少 Pandoc | 建置前 | 安裝並確認 `pandoc --version` | 放入來源不明的預建 EPUB |
| 缺少封面或 metadata | EPUB 建置 | 補齊並確認正式來源 | 建立空白檔騙過檢查 |
| 書稿連結失效 | 工作流驗證 | 修正 Markdown 中的相對路徑 | 從報告刪除錯誤行 |
| 安全 fixture 未如預期阻塞 | 安全驗證 | 修正規則並重跑正負向案例 | 跳過 fixture 繼續封裝 |
| 相同版本已存在 | 發行封裝 | 保留舊包，改用新版本 | 刪除或覆寫既有版本 |
| SHA-256 不符 | 收件驗收 | 回到來源重建新候選包 | 直接修改舊包後重算雜湊 |

每次修正都先改來源，再從失敗節點或整條流程重跑，並在 `workflow-status.md` 記錄產物、阻塞原因與確認人。這能保留問題如何被發現及排除的證據，而不是只留下最後一次成功畫面。

## 驗收候選發行包

若候選包由另一位協作者交付，可不重建內容，先執行只讀驗收：

```powershell
.\examples\06-ebook-publishing\verify-package.ps1 -Version 0.2.1-local
```

驗收腳本確認八項必要檔案、逐檔 SHA-256、manifest 版本、`release-candidate` 狀態與完整來源 commit。它故意不把人工項目改成已完成。自動驗收通過後，出版者仍要開啟 EPUB，在桌面與手機閱讀器檢查封面、目錄、表格、程式碼與連結，再以最新 EPUBCheck 留下正式報告。

最後核對作者、出版者、版權、授權、ISBN 或平台識別碼、價格、銷售地區與上架日期。這些欄位全部有負責人與證據後，才可由 `release-candidate` 進入 `ready-to-submit`；實際上傳仍需要另一個清楚顯示平台、帳號、檔案與外部影響的人工確認。

## 發行與回顧

通過驗證後，依第五章建立版本化發行包，至少包含 EPUB、封面、manifest、SHA-256、變更記錄與測試摘要。讀者 repository 應以固定 tag 或 commit 對應書中範例；正式 URL 與授權未確認前，文件保留待確認標記。

發行後做一次短回顧：哪個節點最常阻塞？哪個輸入契約不清楚？哪些檢查仍依賴人工？回顧結果回寫到 Skill 的測試或治理文件，而不是只留在聊天紀錄。

完整案例的工作流草稿與檢查表見 [`examples/06-ebook-publishing/`](../../examples/06-ebook-publishing/)。

若只想驗證流程而不把練習產物放入正式 `dist/`，可以用 `-OutputRoot` 指定隔離目錄。無論輸出在哪裡，相同版本都不得覆寫；測試結束後也要先確認目標確實是測試目錄，再依團隊規則清理。

## 常見錯誤

- 為了展示自動化而跳過人工出版確認：技術成功不等於授權與身份正確。
- 把所有既有 Skill 複製進新專案：造成版本與責任混亂。
- 先建置 EPUB 再想章節契約：問題會太晚才被發現。
- 只保存最後產物：沒有中間報告就無法追查是哪一階段出錯。
- 把前作 repository 當成新書唯一來源：新書應有自己的版本、授權與讀者說明。

## 練習

以自己的書稿或文件專案為例，畫出五個以上狀態，為每個狀態列出輸入、輸出、阻塞條件與人工閘門。再挑一項專案特有的缺口，寫出最小自訂 Skill 規格，不得把既有驗證能力重新實作一次。

## 本章小結

電子書出版案例顯示，Skill 的價值不在於把所有步驟自動化，而在於讓每個階段的責任、產物與停損點清楚可見。先重用既有能力，補足最小缺口，經過測試與安全閘門後再建立可追溯的發行包，才能把一次性的流程變成可長期維護的工作系統。

下一章會把同一套方法遷移到網頁版教材：保留盤點、契約、驗證與人工閘門，改以導覽、響應式、無障礙與瀏覽器走讀處理媒介差異。這能檢驗真正可重用的是工作方法，而不是只適用於 EPUB 的固定步驟。


# 第 7 章｜完整案例：網頁版教材製作 Skill

## 本章目標

讀者完成本章後，能把前六章的盤點、組合、自建、驗證與治理方法，遷移到網頁版教材製作。你將從內容契約開始，建立一個可在本機瀏覽的靜態教材網站，並能區分自動檢查、人工走讀與正式部署三種不同責任。

這個案例不要求讀者成為前端工程師。重點是判斷哪些既有 Skill 可以重用、哪一小段流程仍有缺口，以及如何讓 HTML、CSS、導覽與練習活動成為可測試、可交接的教材產物。

## 核心概念

- 網頁預覽只是把內容顯示在瀏覽器；完整教材還要有學習目標、順序、練習、回饋與完成條件。
- 內容來源、頁面範本、建置程式與輸出網站應彼此分離，避免為了調整版面而破壞原稿。
- 響應式與無障礙不是最後才補的裝飾，而是輸入契約與驗收標準的一部分。
- 自動檢查可以快速攔截結構、連結與危險內容，但不能代替真實瀏覽器與學習者走讀。
- 本機建置成功只代表形成部署候選版，不代表已獲准公開網站。

## 本章交付

本章會完成一個三頁迷你教材：一個課程首頁、兩個課程單元、共用 CSS、一個程式範例與一個自我檢核活動。案例同時產生內容契約、建置結果、導覽檢查、無障礙基線與安全 fixture 結果；最後狀態停在等待人工核准的部署閘門。

讀者範例位於 [`examples/07-web-learning-material/`](../../examples/07-web-learning-material/)。教材來源放在 `source/`，轉換結果放在 `site/`；建置流程不得覆寫來源檔。這個分界讓作者可以專注修訂 Markdown，版型維護者可以調整範本與 CSS，驗證者則能針對輸出網站重跑檢查。

## 案例背景與範圍界線

假設團隊已經完成一份兩課的 AI Skill 入門教材，希望讀者不安裝電子書閱讀器，也能從瀏覽器依序學習。第一課說明如何盤點現成 Skill，第二課帶讀者判斷採用、組合或自建；每課都有目標、短例子、自我檢核與小結。

本章處理的是可離線建置的靜態網站：HTML、獨立 CSS、少量由專案維護的 JavaScript 與本地素材。範圍不包含會員登入、後端資料庫、學習管理系統（Learning Management System, LMS）、付費、分析追蹤、留言系統或自動正式部署。若專案需要這些能力，應另建需求、風險與隱私評估，不能把它們悄悄塞進教材建置 Skill。

界線也包含內容責任。Skill 可以確認每課是否具備必要欄位，卻不能判定教材在所有情境都正確；它可以找出圖片缺少替代文字，卻不能替作者決定替代文字是否真正傳達教學意義。自動化負責提供證據，內容負責人仍要做最後判斷。

## 先盤點現成 Skill

開始寫轉換程式前，先依第一章的方法查閱本機、團隊與讀者 repository 的 Skill catalog，記錄版本、來源、限制與驗證日期。本案例優先評估以下能力：

| 能力 | 本案例用途 | 初步決策 | 採用界線 |
|---|---|---|---|
| `codex-spark-book-writing` | 整理教材語句與單元結構 | 組合 | 不負責網頁建置與發布 |
| `review-ebook-continuity` | 檢查目標、範例、練習與小結是否連貫 | 組合 | 仍需學習者實際走讀 |
| `publish-ebook-preview` | 提供靜態預覽與導覽觀念 | 微調 | 預覽能力不等同完整教材流程 |
| 瀏覽器檢查能力 | 檢視不同寬度、鍵盤操作與互動 | 組合 | 需要可用的瀏覽器環境與人工判讀 |
| 網站建置／代管能力 | 作為進階部署候選 | 候選 | 只有取得權限並通過閘門後才能使用 |

盤點結果顯示，內容整理、連貫性檢查與靜態預覽已有可重用能力。真正缺少的是一段小型協調流程：讀取課程契約、把各課套入統一版型、建立上一課與下一課導覽，再對固定輸出執行教材專用檢查。因此不需要重造 Markdown 解析器、瀏覽器或代管平台，也不應把現成 Skill 的完整內容複製進新專案。

若讀者環境沒有表中的某項 Skill，先把它標為「未取得」，再以現有命令完成最短路徑。名稱相同也不代表版本與能力相同；在 inventory 沒有來源與測試證據前，只能列為候選，不能宣稱已驗證。

## 區分預覽頁與完整網頁教材

兩者都可能顯示相同文章，但完成定義不同：

| 面向 | 電子書預覽頁 | 完整網頁教材 |
|---|---|---|
| 主要目的 | 讓讀者試讀或了解書籍 | 引導讀者完成一段學習任務 |
| 內容結構 | 摘錄、簡介、購買連結 | 目標、概念、範例、練習、回饋、小結 |
| 導覽 | 可前往章節或外部頁面 | 顯示目前位置與上一課／下一課 |
| 互動 | 通常以閱讀為主 | 至少有可操作的自我檢核活動 |
| 驗收 | 頁面可開啟、連結可用 | 還要檢查學習順序、鍵盤操作與完成條件 |
| 發布狀態 | 網頁預覽候選 | 教材部署候選 |

如果只有把 Markdown 轉成 HTML，卻沒有課程順序、學習目標與檢核活動，它仍是預覽頁。反過來，加入大量動畫也不會自動成為教材；互動必須服務明確的學習行為，並在 JavaScript 無法執行時保留可閱讀的核心內容。

## 定義內容模型與輸入輸出契約

三頁案例用一份課程資料描述標題、簡介與課程順序，再以兩份 Markdown 保存課程正文。每一課至少包含穩定識別碼、標題、學習目標、核心概念、範例、檢核活動與小結。識別碼供路徑與導覽使用；可見標題即使日後修訂，也不應造成既有連結無故失效。

| 類別 | 契約內容 |
|---|---|
| 必要輸入 | 課程設定、兩課 Markdown、頁面範本、獨立 CSS 與本地素材 |
| 可選輸入 | 經核准的程式範例、圖片與補充連結 |
| 建置輸出 | `site/` 中的首頁、課程頁、樣式、腳本與素材 |
| 驗證輸出 | 內容、導覽、無障礙基線與安全檢查結果 |
| 阻塞條件 | 缺少必要欄位、重複識別碼、無效路徑、危險內容或建置失敗 |
| 外部副作用 | 預設為無；不推送 repository、不啟動正式部署、不修改 DNS |

契約還要說清楚「不做什麼」。轉換流程不改寫來源 Markdown，不從網路下載不明腳本，不猜測正式網址，也不把檢查失敗的輸出標成可部署。這些負面條件能避免工具雖然產生檔案，卻在安全與治理上製造更大的問題。

## 設計資訊架構與頁面責任

首頁負責說明課程對象、先備條件、學習成果與課程目錄；課程頁負責呈現單一學習任務。每一頁都使用清楚的頁首、主要導覽、主要內容與頁尾區域。課程頁在標題附近顯示目前課次，底部提供上一課與下一課；第一課沒有上一課時不產生空連結，最後一課則清楚標示課程結束。

標題階層代表內容關係，而不是字體大小。每頁只有一個主要標題，子主題依序向下；若只是要縮小字級，應改 CSS，不應跳過標題層級。連結文字要說明目的，例如「前往第二課：判斷採用方式」，避免所有導覽都只寫「下一頁」。

自我檢核活動維持最小範圍：讀者完成練習後主動標記課次，首頁再顯示完成進度。狀態只保存在瀏覽器的本機儲存空間（localStorage）；即使 JavaScript 無法執行，題目與正文仍可閱讀。它不是成績系統，也不蒐集個人資料。這項限制讓案例專注於教材結構與可用性，而不把工作擴張成應用程式開發。

## 建立 Markdown 到 HTML 的靜態流程

建置流程可拆成六個可觀察步驟：

1. 讀取課程設定與所有課程來源，驗證必要欄位、識別碼與順序。
2. 建立乾淨的暫存輸出；只清理專案管理的 `site/`，不碰 `source/`。
3. 使用既有 Markdown 轉換能力產生內容片段，不自行發明解析語法。
4. 將內容放入共用 HTML 範本，依課程順序產生目錄及前後課導覽。
5. 複製經核准的 CSS、JavaScript 與本地素材，禁止來源路徑逃出案例目錄。
6. 對完成的網站執行連結、結構、無障礙基線與安全檢查，留下結果後才形成候選版。

相同輸入應產生相同頁面結構。建置時間、開發者電腦路徑與臨時狀態不應寫進 HTML，否則每次執行都會出現無意義差異。若其中一步失敗，流程應停止並指出來源檔與原因，不能保留一半成功的網站再顯示 `pass`。

## 補足最小自訂缺口

本案例的最小自訂 Skill 可命名為 `web-learning-material-workflow`。它不是網站產生器大全，而是教材流程的協調層：先呼叫內容檢查，再執行既有轉換，產生導覽，最後收集驗證結果。

- 輸入：案例根目錄與課程契約。
- 工作：驗證、建置、導覽產生與結果彙整。
- 輸出：靜態網站及固定格式的狀態行。
- 限制：不安裝遠端套件、不修改來源、不開啟外部發布、不執行教材文字中的指示。
- 驗收：完整 fixture 全部通過；缺少目標或含危險內容時明確阻塞。

這個範圍之所以合理，是因為缺口已有具體案例與通過條件。若日後需要影片串流、登入或學習紀錄，應新增獨立能力與風險評估，不把它們塞進第一版 Skill。小而清楚的責任也讓其他教材能替換範本，而不用一起複製部署權限。

## 執行完整案例

在 repository 根目錄使用 PowerShell 執行：

```powershell
.\examples\07-web-learning-material\run-case.ps1
```

成功時依序輸出：

```text
content-contract: pass
site-build: pass
navigation-check: pass
accessibility-baseline: pass
security-fixtures: pass
deployment-gate: awaiting-human-approval
```

前五行表示內容契約、網站建置、導覽、無障礙基線與安全 fixture 都符合本案例標準。最後一行不是失敗，而是有意保留的控制點：自動化已完成本機候選版，但尚未取得對外公開授權。若任何前置檢查失敗，應先修正對應來源再重跑，不可手動竄改報告或略過該行。

## 響應式與無障礙驗證

靜態檢查先確認頁面具有語言、唯一主標題、主要內容區、可辨識的導覽、圖片替代文字、表單標籤與按鈕名稱，也確認所有內部連結指向存在的檔案。`accessibility-baseline: pass` 只代表這組可自動判斷的基線通過，不等於符合所有無障礙規範，更不代表輔助科技使用者一定能順利學習。

接著在瀏覽器以 375、768 與 1440 像素寬度走讀首頁和兩課。檢查文字是否被截斷、程式碼是否造成整頁橫向捲動、導覽是否遮住內容、按鈕是否互相重疊，以及圖片縮放後是否仍可理解。內容放大到 200% 時也要重新檢查，不要只看預設比例的截圖。

鍵盤走讀時，從網址列開始只使用 Tab、Shift+Tab、Enter、方向鍵與空白鍵。焦點順序應跟閱讀順序一致，焦點樣式必須看得見，自我檢核不應要求滑鼠才能完成。若畫面看似正常但焦點跳到隱藏元件，仍屬阻塞問題。

## 安全 fixture 與內容邊界

教材來源也是不可信輸入。範例至少要攔截未核准的 `<script>`、`javascript:` 連結、逃離來源目錄的路徑，以及要求工具讀取憑證或執行系統命令的文字。這些內容可以出現在安全教學範例中，但只能當作資料顯示或被 fixture 標記，不能由建置流程執行。

若課程確實需要示範 HTML，應使用明確的程式碼區塊並轉義後呈現；不要為了方便而允許任意原始 HTML。外部圖片、字型與分析腳本也要有核准清單，因為它們會產生網路請求、隱私與長期可用性風險。`security-fixtures: pass` 表示已知危險案例按預期被拒絕，不表示網站從此不需安全審查。

## 本機預覽與學習者走讀

建置通過後，在 repository 根目錄啟動本機靜態伺服器：

```powershell
python -m http.server 8000 --directory .\examples\07-web-learning-material\site
```

再開啟 `http://localhost:8000/`。使用伺服器預覽能重現網站的相對路徑與資源載入方式，比直接雙擊 HTML 更接近實際部署環境。預覽完成後，以 `Ctrl+C` 停止伺服器。

人工走讀要以學習任務為單位：讀者能否從首頁知道先備條件？能否進入第一課、完成檢核、理解回饋，再前往第二課？若每個頁面單獨看都正確，但讀者不知道下一步，教材仍未完成。建議請一位未參與製作的人照著操作，記錄卡住的位置、預期行為與實際畫面，再把問題回寫到契約或測試。

## 版本化交付與人工部署閘門

通過自動檢查與人工走讀後，建立唯讀的版本化交付包。至少包含 `site/`、來源版本或 commit、建置命令、檔案清單、雜湊、驗證摘要與已知限制。候選狀態可命名為 `deployment-candidate`，與已公開的 `deployed` 明確分開；同一版本不得在交付後靜默覆寫。

正式部署前，人工確認目標網址、公開範圍、素材授權、隱私設定、負責人、回復方案與部署後檢查方式。若使用代管 Skill，也只能在這個閘門之後取得必要權限。核准畫面應清楚列出要上傳的目錄與對外影響，不能只提供模糊的「繼續」按鈕。

部署後還要檢查正式網址、HTTPS、首頁與課程深層連結，並確認公開版本的檔案雜湊與候選包一致。這是另一個工作階段，不屬於本章範例的自動執行範圍，因此整合案例刻意停在 `deployment-gate: awaiting-human-approval`。

## 與第 6 章比較

兩個案例使用相同治理骨架：先定義產物，盤點既有能力，補最小缺口，執行正向與負向測試，建立候選包，最後停在人工核准點。差異來自媒介，而不是把所有流程重寫一次。

| 第 6 章電子書 | 第 7 章網頁教材 |
|---|---|
| 主要產物是 EPUB、封面與商店資料 | 主要產物是 HTML、CSS、腳本與本地素材 |
| 驗證封裝、目錄與閱讀器相容性 | 驗證導覽、響應式、鍵盤操作與互動 |
| 候選狀態為 `release-candidate` | 候選狀態為 `deployment-candidate` |
| 人工閘門確認書籍身份與商店欄位 | 人工閘門確認網址、授權、隱私與公開範圍 |

內容編輯、版本追溯、雜湊與不可信輸入處理可以重用；EPUB CSS 與網頁 CSS 則應分開維護。這個對照證明 Skill 的可重用性來自清楚契約，而不是把同一套指令硬套到不同產物。

## 常見錯誤

- 把預覽頁直接稱為完整教材：缺少學習路徑、練習與完成條件。
- 先寫大型網站框架再定內容契約：技術選擇會反過來綁架教材需求。
- 自行解析 Markdown：重複製造既有工具已解決的問題，也增加安全風險。
- 只看桌面截圖：手機寬度、內容放大與鍵盤焦點問題容易被漏掉。
- 把自動基線當成完整無障礙認證：機器無法判斷所有語意與學習效果。
- 讓教材內容直接注入 HTML 或執行命令：來源文字不能取得建置環境權限。
- 本機成功後自動公開：網址、授權、隱私與回復方案仍需人工確認。
- 建置時修改 `source/`：輸出問題會污染可維護的教材原稿。

## 練習

選一份自己的短篇教材，規劃首頁加兩課的資訊架構。為每課寫出目標、核心概念、範例、自我檢核與小結，並建立一張輸入輸出契約表。接著列出你已經擁有的內容整理、Markdown 轉換、瀏覽器檢查與部署能力，對每一項標記採用、組合、微調、自建或未取得。

不要立刻實作全部功能。先挑出一個無法由現成能力處理的最小缺口，為它寫輸入、輸出、限制、完整 fixture 與失敗 fixture。最後設計六項驗收：內容契約、建置、導覽、無障礙基線、安全與人工部署閘門，並說明哪些結果能由機器判定、哪些必須請學習者實際走讀。

## 本章小結

網頁版教材案例把本書的方法從固定格式的電子書延伸到可導覽、可互動、可調整版面的靜態網站。做法仍從盤點開始：重用內容與預覽能力，只為教材契約、導覽和驗證補上最小協調層；再以響應式、無障礙、安全 fixture 與人工走讀建立證據。

完成建置並不等於完成公開。把來源、輸出與權限分離，讓候選版停在人工部署閘門，才能兼顧可重跑與可控制。至此，讀者已用兩種不同媒介驗證同一套 Skill 工作方法：能力能否長期重用，取決於契約、證據與治理是否清楚，而不是自動化步驟有多少。
